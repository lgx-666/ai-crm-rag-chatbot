### 2.*阐述function calling工具定义的基本信息，如function calling工具搭建的基本流程，定义的函数功能*

#### 2.1工具定义方式

在项目中，*Function Calling* 工具的定义主要采用两种方式：

**方式一：使用 *LangChain* 的 `@tool` 装饰器（早期原型 `tools.py`，已归档到 `../_archive_main_flow/`，生产代码走方式二）**

```python
from langchain.tools import tool

@tool
def get_user_info(phone_number: str) -> str:
    """根据手机号查询用户基本信息。"""
    info = get_user_info_from_db(phone_number)
    if info:
        return f"姓名: {info['name']}, 年龄: {info['age']}, 职业: {info['occupation']}, 兴趣: {info['interest']}"
    return f"未找到手机号 {phone_number} 的用户信息"
```

`@tool` 装饰器会自动将函数转换为 *LangChain* 的 `StructuredTool` 对象，并提取 *docstring* 作为工具描述，参数类型从函数签名推断。

**方式二：使用 `StructuredTool.from_function` 工厂方法（`function_calling_handler.py`）**

```python
from langchain.tools import StructuredTool

def _get_user_info() -> str:
    info = get_user_info_from_db(phone_number)
    if info:
        return f"姓名: {info['name']}, 年龄: {info['age']}, 职业: {info['occupation']}, 兴趣: {info['interest']}"
    return f"未找到手机号 {phone_number} 的用户信息"

get_tool = StructuredTool.from_function(
    func=_get_user_info,
    name="get_user_info",
    description="查询当前登录用户的个人信息，不需要任何参数。"
)
```

#### 2.2工具定义的基本流程

**定义功能函数**：编写完成特定业务逻辑的 Python 函数（如查询用户信息、更新用户信息）。

**包装为 LangChain 工具**：使用 `@tool` 装饰器或 `StructuredTool.from_function` 将函数包装成工具对象，并明确其名称、描述和参数说明。

**绑定到大模型**：在调用大模型时，通过 `bind_tools()` 方法将工具列表传递给模型，使模型具备调用这些工具的能力。

**处理工具调用响应**：模型返回 `tool_calls` 后，解析工具名称和参数，执行对应的函数，并将执行结果以 `tool` 角色消息返回给模型，最终生成自然语言回答。

#### 1.3 项目中定义的函数功能

| **工具名称**     | 功能描述                                             | 输入参数                                                     | 输出                   |
| :--------------- | :--------------------------------------------------- | ------------------------------------------------------------ | ---------------------- |
| get_user_info    | 查询当前登录用户的个人信息（姓名、年龄、职业、兴趣） | 无（通过闭包绑定 `phone_number`）                            | 格式化的个人信息字符串 |
| update_user_info | 更新当前登录用户的个人信息                           | `name`（可选）、`age`（可选）、`occupation`（可选）、`interest`（可选） | 更新成功或失败的提示   |

​	这些工具在 `function_calling_handler.py` 中被实际使用，当意图识别为 `4` 时，系统会调用该处理函数，让模型自主决定是否调用工具以及如何调用。

### 3.*RAG存储的内容描述，调研RAG有哪些优化方式，并阐述怎么跟本项目进行融合*

#### 3.1 RAG 存储内容描述

​	项目中的 RAG 知识库使用 **Chroma 向量数据库** 进行本地持久化，路径由 `config.CHROMA_PERSIST_DIR` 指定，当前为 `./data/chroma_db_v2`（`_v2` 是修复文本分块缺陷之后重建的库，旧库已删除）。集合空间度量为余弦（建集合时写入 `metadata={"hnsw:space": "cosine"}`）。包含两个集合：

| 集合常量 | 集合名 | 存储内容                                                     | 数据来源                                                     |
| -------- | --------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| COLLECTION_MARKET | market_knowledge | 大模型知识点（Transformer、LLM、RAG、分布式训练、微调/RAG 面等） | 51 篇课程 PDF，经 `import_knowledge.py` 批量导入（当前 656 块） |
| COLLECTION_COURSE | java_knowledge   | Java 后端八股文（JVM、并发、Spring、MySQL、Redis、设计模式等） | `Java 面试知识点总结.pdf`（当前 16 块）                        |

​	每个文档在存入时会被切割成 **文本块（chunk）**，参数为 `chunk_size=500` 字符、`overlap=50` 字符，另有 `min_chunk=30` 的短块门槛（页眉、"扫码加查看更多"这类无信息行直接丢弃，否则短句会以高相似的身份抢走正文的召回位）。切分逻辑在 `file_loader.chunk_text`：逐行清洗后按**固定步长** `stride = chunk_size - overlap` 聚合落块，遇到超长单行（PDF 整段不换行）先落缓冲块、再对该行做定长滑窗。

当前库的实测规模与块长度分布：

| 集合 | 块数 | 嵌入维度 | 块长 中位数 | 块长 最短/最长 | ≥400 字符占比 |
| --- | --- | --- | --- | --- | --- |
| market_knowledge | 656 | 768 | 517 | 55 / 586 | 94.7%（621/656） |
| java_knowledge | 16 | 768 | 512 | 215 / 540 | 93.8%（15/16） |

每个块存储：

- **文本内容**（用于向量化和检索）
- **嵌入向量**（由本地 `BAAI/bge-base-zh-v1.5` 生成，768 维，中文语义优于 Chroma 默认的英文 `all-MiniLM-L6-v2`。踩过的坑：`client.get_collection()` 不会可靠恢复持久化时的 embedding function，会静默退回默认 384 维模型，导致查询时抛 `InvalidDimensionException`——所以读写两侧都必须显式传入同一个 embedding 函数，`db/vector_db.py` 已按模块级单例处理）
- **元数据**（`source` 来源文件名；`import_knowledge.py` 另存 `path`，`/upload_knowledge` 另存 `collection`，用于回答末尾的引用溯源）

检索时，用户问题先经 `kb_router.retrieval_plan` 做主题路由，再在选中的集合里按余弦相似度取最相似的块：**判为单域时该域独占 4 个槽位（`TOP_K_SINGLE=4`），判为双域或难以区分时两域各取 2 条（`TOP_K_SHARED=2`），总槽位恒为 4**，既去掉跨域噪声又不撑大 prompt。取回的块去重后拼接成上下文，与用户问题一起提交给大模型生成回答。

#### 3.2 RAG 优化方式调研及融合方案

| 优化方式                        | 描述                                                         | 本项目融合方案                                               |
| ------------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| **分块策略优化**                | 调整 `chunk_size` 和 `overlap`，使块更贴合语义单元           | **已落地（本轮收益最大的一项）**：除 `500/50` 参数外，修复了 `chunk_text` 的**步长塌缩**缺陷——原实现 `start = max(end - overlap, start + 1)` 在断句点紧贴块起点时步长退化为 1，同一句话被"每次少一个字符"地重复切出大量 1~40 字的近重复块（旧库 6197 块中约 4110 块、即 66% 属此类）。现改为固定步长 `stride = chunk_size - overlap`，与标点位置彻底解耦，并用 `min_chunk=30` 门槛清掉无信息短句。重建后的块长分布见 3.1。 |
| **混合检索（Hybrid Search）**   | 结合向量检索（语义）和关键词检索（BM25/TF-IDF），提高召回率  | Chroma 原生支持 `where` 过滤，但混合检索需要额外集成。可在 `query_collection` 中先进行向量检索，再用关键词过滤或结合 `rank_bm25` 对结果重排序。 |
| **重排序（Re-ranking）**        | 使用专用模型（如 `cross-encoder`）对初筛结果重新打分，提高精准度 | 在 `get_response_from_vectorstore` 中，先检索 Top-10，再用轻量级重排序模型（如 `ms-marco-MiniLM-L-6-v2`）筛选 Top-3，提升最终上下文质量。 |
| **查询重写（Query Rewriting）** | 用大模型将用户问题改写为多个不同表述，分别检索后合并结果     | 在 `handle_other_intents` 或 RAG 分支中，可调用 LLM 生成 2-3 个同义问题，并行检索后融合结果，提升鲁棒性。 |
| **元数据过滤**                  | 根据用户信息（如兴趣）或文档标签提前过滤集合                 | 在 `query_collection` 中增加 `where` 参数，例如只检索与用户兴趣相关的文档，减少噪声。 |
| **多路召回 → 主题路由**          | 同时从多个集合检索并合并结果                                 | **已落地并升级**：固定"双库各取 top-2"会让另一个域的块稳定地污染上下文（两库内容分属大模型与 Java，任何一题只该从一个域取材）。现由 `kb_router.retrieval_plan` 按关键词计分决定单域独占 4 槽或双域各 2 槽；`response_generator.py` 与 `eval_rag.py` 共用同一份检索计划，保证评估测的就是线上链路。 |
| **缓存机制**                    | 对热门问题缓存回答或检索结果                                 | **已落地**（实现与设计取舍见 5.2）。最终实现与本行最初的设想有三处不同，且都是被实测逼出来的：① 挂在 **LangGraph 节点边界**而不是 Flask 路由层，且**读在意图分类之前**——命中时把分类与生成两次 LLM 调用一起省掉；② key 里**故意不含 `phone_number`**，只含 `normalize(query)`、用户**画像签名**与**配置指纹**（`CONFIG_FP`，2026-11-07 补），含了手机号就等于零跨用户命中、还把 PII 写进 key；③ 有效期 **3600s**，不是 10 分钟。 |
| **异步处理**                    | 将向量化生成和检索放入后台任务，不阻塞主线程                 | 当前为同步，可改造为异步，但考虑到服务并发不高，暂不优化。   |

**具体融入方式**：上表中**"分块策略优化""多路召回 → 主题路由"两项已在 RAG 这一轮落地**（效果与量化数据见 3.3），**"缓存机制"也已落地**（设计与实测数字见 5.2）；其余为调研后待实施的候选项，对应挂接位置如下——

- 在 `response_generator.py` 的 `get_response_from_vectorstore` 中，可增加对 `query_collection` 的 `where` 参数支持，实现元数据过滤。
- 在 `db/vector_db.py` 的 `query_collection` 中，可添加重排序逻辑，使用 `sentence_transformers` 的 CrossEncoder 模型。
- 在 `graph_flow.py` 的 `rag_node` 中，可对 `intent == 1` 的查询先进行查询重写，再并行检索。

#### 3.3 RAG 效果量化评估（RAGAS 四指标）

**评估设置（第一轮，6 题，2026-10-03）**：脚本 `eval_rag.py`，6 条课程领域问题，每条配人工撰写的标准答案（reference）。裁判模型取 `.env` 的 `MODEL_NAME`（**那轮为 `qwen-plus`**）且 `temperature=0`（保证打分可复现）；`answer_relevancy` 需要的 embedding 用本地 `bge-base-zh-v1.5`，不额外消耗额度。检索与生成**复用线上链路**——`eval_rag.py:138` 与 `response_generator.py:65` 调用同一个 `kb_router.retrieval_plan`，若评估脚本自己硬编码"双库各 top-2"，测的就是已经不存在的旧管线，结论无效。执行串行（`RunConfig(max_workers=1, timeout=600)`，该档位可在初始提交 `324f05f` 的 `eval_rag.py:196` 复核），6 样本 × 4 指标。

> ⚠️ **本节只描述第一轮（6 题 / 裁判 `qwen-plus` / 串行 600s）**。第二轮 9 题（2026-10-07，裁判换成 `qwen3.8-max`、`2 并发 × 1800s`）见 3.3.1，两轮换了一把尺子，**跨节只能看方向，不能把差值当提升幅度**。
> 另需如实说明证据强度：这四份留档 csv 的表头只有 `user_input`…`context_recall` 共 8 列，**没有 `judge_model` 等落款列**（那六列是 10-08 提交 `ed80ce6` 才追加的），所以"这轮裁判是 `qwen-plus`"目前由 `eval_rag.py:255-257` 的注释与本段文字记录，csv 数据本身不带这个字段。

**修复前后对比**（同一批 6 题；基线留档 `data/ragas_report_baseline_20260928.csv`，修复后留档 `data/ragas_report_v2_20261003.csv`）：

| 指标 | 修复前 | 修复后 | 变化 | 该指标在测什么 |
| --- | --- | --- | --- | --- |
| faithfulness | 0.4183 | **0.9290** | +0.5107 | 回答是否只依据检索到的上下文（幻觉程度） |
| answer_relevancy | 0.5473 | **0.7127** | +0.1653 | 回答切不切题（反向生成问题后算向量相似度） |
| llm_context_precision_with_reference | 0.4722 | **0.9167** | +0.4444 | 召回上下文中相关块的占比与排序 |
| context_recall | 0.1667 | **0.5506** | +0.3839 | 标准答案里的论断有多少能被召回上下文支撑 |

**两项改动各自的证据**（一次评估同时测了两项，但数据里能把它们分开看）：

1. **分块修复 → 主要抬 `faithfulness` 与 `context_recall`**。旧管线召回到的往往是 1~40 字的近重复碎片：修复前第 1 题的 4 个块合计只有 **47 字符**，而模型却生成了 988 字答案——没有内容可依据时模型转向自身先验作答，该项 `faithfulness` 只有 0.0606。修复后每题上下文规模约 1800~2150 字符，与 3.1 的块长分布一致。**需要如实说明：`faithfulness` 从 0.06 到 1.0 的实质是"上下文里终于有了可供忠实的内容"，不代表模型行为本身变好。**
2. **主题路由 → 主要抬 `llm_context_precision`**。修复前第 3、4 题的块数是不规整的 3 条（双库各 top-2 去重后的典型形状），修复后全部是整齐的 4 条单域块。跨域噪声被移除后精准度从 0.4722 升到 0.9167。另有只读复测佐证：10 题共 40 个槽位 **0% 跨域**、目标块均排第 1。

**已知边界与统计口径**（这两点决定了为什么到此为止）：

- `context_recall` 仍只有 0.5506，最低两题是"文本分块策略"(0.30) 与"多轮对话长期记忆"(0.375)。它们的 `reference` 是 9 项、8 项的长列举，而 4 个槽约 2100 字符的上下文装不下完整清单——瓶颈是**上下文预算与标准答案粒度**的矛盾，不是检索质量。再抬需要增大 top_k 或做查询分解，代价是 token 成本与首字延迟上升，收益不划算。
- 样本量 n=6，单个指标点约 0.167。因此只有 +0.38 量级以上的差异具备解释力；逐条之间 0.05 量级的排序差异（如第 6 题 0.6260 与第 2 题 0.6783 的 `answer_relevancy`）不具统计意义，不应据此调参。
- **评估集自身的覆盖缺口**：这 6 题经路由后**全部判为单域 `market`（各 4 槽）**，没有一个走到"双域各 2 槽"分支，也没有一道考察 `java_knowledge`。因此本次四指标只能证明"大模型域内的检索质量"，跨域分支只由 `tests/test_kb_router.py` 的单元测试覆盖。该缺口已在下方 3.3.1 补齐（Q7/Q8 单域 java、Q9 跨域双查）。
- 一轮评估同时改动两处会让归因变模糊，本项目靠上面的"块数/块长形状"证据链拆开；后续再优化时应保持**一次只动一个变量**。

**三条结论**：

1. **跨域分支在"检索侧"是通过的，问题在生成侧越界。** Q9 的 `ctxprec` 1.0000、`ctxrec` 0.8571
   是全表最高召回覆盖，说明 `market ×2 + java ×2` 这条路确实把两域该检的块都检回来了：
   4 条召回块（合计 2072 字符）逐条看是 [1] RAG 服务链路、[2] RAG 痛点与解决策略（market 侧）、
   [3] `synchronized`/monitor/临界区、[4] Collection 与 Collections（java 侧），域与内容都对得上。
   但 `faithfulness` 只有 **0.2826**。**需要澄清一个容易读错的地方**：答案里 5 处引用标记
   全部指向 `[3]`，而 `monitor`、"被阻塞的线程无法被中断"这些 Java 论断本来就写在 `[3]` 里，
   是**有**依据的；`Faithfulness` 判定的是"逐条声明能否由召回上下文推出"，与有没有打引用标记无关，
   所以扣分的不是"没标引用"，而是答案超出这 2072 字符之外自行扩展的部分——模型把一道跨域题
   写成了两大部分、三节标题的 975 字教程，其中"哪些位置适合加锁、哪些不建议加锁"这类工程建议
   和把 [1] 的链路复述后继续展开的细节，在上下文里没有对应文本，全部计为无据。
   **结论：缺陷定位在生成提示的"依据上下文作答、不要自行扩展"这条边界约束上，不在 `kb_router`。**
   另附一条方法论提醒：引用标记数与 `faithfulness` **不相关**（Q2/Q8 各只有 5 处标记，faith
   却是 1.0000/0.9500；Q4 有 15 处标记，faith 只有 0.6341），所以不能拿"引用密度"当忠实度的
   代理指标——本项目一开始差点据此误判，实际数据否掉了它。
2. **均分曾经虚高 0.0927，成因是缺失而非质量。** 主跑（`max_workers=4 × timeout=900`）有
   7 格超时，ragas 把失败的格子留成 `NaN` 并在求均值时**剔出分母**，于是 `faithfulness`
   显示为 0.9105（n=5/9），补跑那 4 格后真实值是 **0.8178**（n=9/9）。缺失也非随机：
   `faithfulness` 要把答案拆成逐条声明再判定，答案越长声明越多、单 job 越久，越容易撞超时。
   因此脚本现在强制打印 `mean + n`——**n 不等于题数就说明该分数不可用**。
3. **`context_recall` 仍是短板（0.5817），且瓶颈未变。** 最低两题 Q5(0.2000)、Q4(0.2222)
   的标准答案是 8~9 项长列举，而 4 槽约 2100 字符的上下文装不下完整清单；对照 Q8（标准答案
   只 3 个论断、298 字）得 1.0000。这与 3.3 的结论一致：**瓶颈是上下文预算与标准答案粒度的
   矛盾**，要靠加大 top_k 或查询分解来解，代价是 token 与首字延迟，暂未做。

**运行失败率与档位教训**：同一批数据，`4 并发 × 900s` 主跑死 7/36 格，补跑降到
`2 并发 × 1800s` 后 **7/7 全通、总耗时 1499s**。其中 4 格（Q1/Q3/Q4 的 faithfulness 与
Q3 的 ctxrec）在同一秒 `18:42:18` 报 `TimeoutError`，是一次网络抖动同时打在并发 worker 上；
另 3 格都是题序最后的 Q9，属排队尾部超时。**结论：在思考型慢模型上，并发是风险而非收益**，

**运行形态（每条都能回代码核对）**

| n=1 | 0.85 req/min | 1.7 | 4.2 | 8.4 |
| n=2 | 1.7 | 3.4 | 8.5 | 16.8 |
| n=5 | 4.3 | 8.5 | 21 | 42 |
| n=10 | 8.5 | 17 | 42 | 84 |

**进程内并发实测（2026-11-07，`_lab_load.py`，0 token，宿主 venv）**

上面那张表是推导。这一节是把推导里**能在进程内验证的那一层**真的打了一遍：N 个线程各持一个
`app.test_client()`，用 `threading.Barrier` 卡住后同时发车，读完整条 SSE 流（到 `data: [DONE]`）才算结束；

**为什么能不花钱**：只在**客户端那一层**打桩——替掉 `response_generator.client` 与 `intent.client`，不是替掉函数。

**"吞吐不随 N 上升"是谁造成的：六层对照（同一进程、同一批 N，每层只多一个真实依赖）**

压测进程里另外注册了六个只在本进程存在的 `lab_*` 路由（**不改 `app.py`**）：

| `/lab_graph` | 完整 `chat_graph.stream()`（走缓存命中路径） | 0.028 | 0.286 | 44 |

两个直接结论：

- **单步掉得最狠的是"加两条 INSERT + commit"**：218 → 52 req/s。成因是 sqlite 的**单写者串行**，不是索引、不是 IO。
- **进程内最紧的那道墙是检索：~19 req/s**，而且它在 N=1/2/5/10/20 上分别是
  **19.31 / 21.07 / 19.25 / 18.57 / 18.96** ——**完全不随并发变化**，正是 GIL 下 bge 编码不并行的形状；
  p50 从 51ms 涨到 1.017s（20 路排队），但**吞吐不动**。

用实测的 A=19（检索层）、B=52（DB/图层）得 **13.9 req/s**，而 `/chat` 未命中组实测
**13.60 / 13.60 / 14.06**（N=5/10/20）⇒ **闭合在 2% 以内**。这条把 13.9 从拟合变成可核对的加法，
也说明这一档的进程内上限**由检索决定、DB 层第二**。

**一个被自己打掉的假设：`journal_mode=WAL` 不是解药**

瓶颈 4 原先写的是"扩容顺序：先 `PRAGMA journal_mode=WAL`"。对照实验（**只改这一个 PRAGMA**，
同一临时库、同一代码、同一 N=20，排在整轮压测最后以免污染默认档）：

| journal_mode | 墙钟 | 吞吐 | p50 | p95 | 错误 |
|---|---|---|---|---|---|
| `delete`（sqlite 默认：写时建回滚日志、提交 fsync） | 0.376 s | **53.23 req/s** | 0.213 | 0.351 | 0% |
| `wal` | 0.841 s | **23.79 req/s** | 0.169 | **0.719** | 0% |

⇒ **吞吐 ×0.45、p95 翻倍**，只有 p50 好一点（0.213 → 0.169）。读法：WAL 让**单个读者**不必等写锁，
但给每次提交加了 checkpoint 与 `-wal` 文件维护，在"20 路并发、每路 2 写"这个形态上净亏。
**串行来自 sqlite 的单写者约束，WAL 移不掉它**——它移掉的是"写阻塞读"，而这个形态里读本来就不是瓶颈
（`/lab_read` 218 req/s vs `/lab_sql` 52 req/s）。瓶颈 4 的扩容顺序已按实测改写（见下）。

**预测里的 `database is locked` 一次都没出现**：15 组共 76 个请求 + 六层对照（N 最高 20）错误率全 0。
每次写是 ms 级、sqlite 默认 busy timeout 5s，串行队列根本走不到超时。**外推（不是实测）**：
要撞 5s 超时得有几百个并发写者排队，而那之前进程内早就先撞检索那道 ~19 req/s 的墙了。

**这份数字不能用来推什么（射程，六条）**

1. **没有 HTTP 服务层**：`test_client()` 不过 werkzeug 的 socket / WSGI 队列 ⇒ 量不到 accept 队列、
   连接数上限、gunicorn worker 数这些**真正的入口瓶颈**。瓶颈 2 那条"没有背压"仍然是推断。
2. **模型耗时是合成的 `sleep`** ⇒ 量不到百炼侧 TPM/QPS 限流、429 重试、真 ttft 抖动。
   生产未命中 16~70s 里绝大部分是这一段，**所以生产的 p95 一定远高于本表**。瓶颈 1 仍然是天花板。
3. **埋点是关的**：生产容器里 `ENABLED=True`，每请求多两个 span 的构造与异步上报 ⇒ 本表偏乐观。
4. **Redis 是进程内 dict**：没有网络往返 ⇒ 命中组是**乐观下界**（真 Redis 还要加一次容器网往返）。
5. **SQLite 是临时库、每请求新建连接**：文件锁行为与生产同构，但生产库数据量更大，索引扫描成本不在本表里。
6. **单进程多线程、受 GIL 约束**：生产若起多 worker，本表的争用结论**不能直接外推**
   （多进程还要各自一份 391MB 模型，见瓶颈 2 的内存账）。

**瓶颈按"先撞到"的顺序**

1. **百炼配额是真正的天花板**。未命中一次要串 2 次调用（意图分类 + 生成），并发的单位成本是"调用数"而不是"请求数"。可参考的实测只有离线侧那一条：`eval_rag.py:235-237`——用 ~1952 prompt / 600~950 completion（接近裁判负载）的请求打百炼，**4 并发总耗时 17.5s vs 串行 4 次约 95s，单请求延迟没随并发变差，也没出现 429 / TPM 限流**。这只证明"4 路没问题"，**账号配额档位本项目没有实测数字，所以这里不给具体 RPM/TPM 上限**。思考型模型的 completion 含思考 token，通常先撞的是 TPM 而非 RPM。
2. **内置开发服务器没有背压**。`threaded=True` 且无上限，过载表现是"越打越慢直到 OOM / 句柄耗尽"，而不是拒绝服务——演示规模（个位数并发）够用，对外服务前必须换 `gunicorn --worker-class gevent`。`Dockerfile:41-43` 的注释记了这条约束：**SSE 必须用能逐 token 推流的 worker，普通 sync worker 会把流憋住**。换多进程时记得内存账：4 进程 ≈ 1.6GB 起（每进程一份模型）。
3. **GIL 与单进程内的 CPU 推理**。LLM 等待期间线程只是 sleep，所以并发能力主要"借"在 IO 等待上；而向量编码是 torch CPU 计算，多线程不会让它变快。**这条前提已经量化（2026-10-16 离线脚本 `_lab_retrieval_latency.py`，宿主 venv，0 token）**：单条 query 纯编码中位 **53.1ms**，走线上同一个 `query_collection()` 的"编码 + HNSW 检索"中位 **54.2ms**（检回 4 块 / 2081 字符），即 **HNSW 本身 <2ms**；`init_vectorstores()` 冷启动 8.90s 是**进程级一次性**开销，不落在每个请求上。按单核算编码也能撑 ~18 次/秒（≈1100 req/min），比未命中路径的 0.85 req/min 高三个数量级 ⇒ **CPU 侧确实不是瓶颈，瓶颈在模型侧配额与服务器背压**。
   🔴 **这个"~18 次/秒"现在是实测而不是外推（2026-11-07，`_lab_load.py` 的 `/lab_retr` 层）：N=1/2/5/10/20 上分别 19.31 / 21.07 / 19.25 / 18.57 / 18.96 req/s，完全不随并发变化。**但**结论要改一半**："CPU 侧不是**延迟**瓶颈"仍然成立（相对 16~70s 的模型等待，20 路排队那 1.017s 可以忽略），**而 CPU 侧确实是进程内吞吐的硬顶（~19 req/s）**——它比内置服务器那一层（`/lab_ping` 1292 req/s）紧两个数量级，也比 SQLite 写那一层（52 req/s）紧。所以"瓶颈在模型侧配额与服务器背压"这句只覆盖了**延迟**维度；在**进程内吞吐**维度上，第一个撞到的是 bge 编码。六层对照见上面"进程内并发实测"。
   **那套"对不上"的数现在已经被检索 span 拆开并定位（2026-10-25 容器内真实 trace）**：`retrieval` span 上线后，同一条 trace 里可以直接做减法——`rag` 节点总时长减去 `llm-stream` 生成时长再减去 `retrieval`，剩下的就是"除检索和生成之外的全部开销"。两条样本：**稳态那次** `rag 23729 − llm-stream 23608 − retrieval 111 = 10ms`；**冷启动那次** `rag 13738 − llm-stream 11966 − retrieval 1762 = 10ms`。结论有三条，都要如实分开：
   - 原先怀疑的"每请求 SQLite 画像/历史读取、prompt 组装"**根本不是候选**，它总共只有 10ms 量级——两次减法闭合在同一个数字上，不需要推断。
   - 容器内**稳态检索 111~222ms**，与宿主离线的 54ms 同一量级（差值是 WSL2 文件 IO 与容器 CPU 配额，没有单独量化，不硬归因）。
   - 那 **1.3~2.9 秒属于容器重建后进程内的首次检索**，即 672 块 HNSW 索引第一次从磁盘读进内存的一次性开销，**不落在每个请求上**（同一镜像里后续请求的 `retrieval` 回落到 111ms / 222ms）。也就是说 4.2 早期版本里"1.34~2.9s 未定位"是**把一次性冷读当成了稳态成本**——这是这套埋点纠正的第一个判断。
4. **SQLite 写**。`get_db_connection()` 每次新建连接（`db/sqlite_db.py:63-64`），没开 WAL、也没传 `timeout=`（默认 busy timeout 5s）。每请求 2 条 INSERT（`prepare` 写 user 行 `graph_flow.py:74`、`finalize` 写 assistant 行 `graph_flow.py:146`；**命中路径也一样写两条**，所以 0.1s 那次并没有绕过 SQLite），单条 ms 级，60KB 的库远不到瓶颈；但 rollback-journal 下写会阻塞读。
   🔴 **原来这句后面的两条都被 2026-11-07 的压测打掉了**（原文是"真上去时第一个报错会是 `database is locked`。扩容顺序：先 `PRAGMA journal_mode=WAL`，再考虑换 PostgreSQL。"）：
   - ① **`database is locked` 一次都没出现**：15 组 76 个请求 + 六层对照，N 最高 20，错误率全 0。单次写是 ms 级、默认 busy timeout 5s，串行队列走不到超时。**外推（不是实测）**：要撞超时得有几百个并发写者，而那之前进程内先撞检索那道 ~19 req/s 的墙。
   - ② **WAL 不是解药，是净亏**：只改这一个 PRAGMA 的对照里，`/lab_sql` N=20 的吞吐**53.23 → 23.79 req/s（×0.45）**、p95 **0.351 → 0.719**（p50 反而 0.213 → 0.169）。串行来自 sqlite 的**单写者约束**，WAL 移掉的是"写阻塞读"，而这个形态里读本来就不是瓶颈（`/lab_read` 218 req/s vs `/lab_sql` 52 req/s）。
   **扩容顺序改成**：先减写次数（`prepare` / `finalize` 那 2 条 INSERT 能不能合并成 1 条、或异步落盘），再考虑换 PostgreSQL；**`PRAGMA journal_mode=WAL` 只在"读多写少且读确实被写阻塞"时才值得开，本项目这个形态上实测是净亏的，不要照抄这条建议**。数字见上面"进程内并发实测"的 journal_mode 对照表。
5. **Redis 不会是瓶颈**，也是全链路唯一"并发越多越省"的一环：命中 0.1s、客户端超时 0.5s（`qa_cache.py:76-77`）、`--maxmemory 64mb --maxmemory-policy allkeys-lru`（`docker-compose.yml:33`）。

**结论档位**

- 课程 / 演示规模（同时在线 ≤5、问题高度重复、走缓存）：当前单容器形态可支撑，量级在**几十 req/min**（见上表 h≥50% 各行）。
- 未命中为主且并发 ≥10：先撞百炼配额、再撞内置服务器，两者都不是加代码能解决的。落地顺序 **#32（关闭思考模式压 W——2026-10-25 已在意图分类与滚动摘要两处落地，单次账单 ¥0.1159→¥0.0916；剩下的 85% 在主答案 `llm-stream`，**已于 2026-11-03 一并关掉**：端到端 58.62s→16.55s、单次账单 ¥0.110→¥0.037，见 5.1.2；⚠️ 它是**带着"质量未验证"这条边界上线的**——11-05 那趟付费跑同时动了生成上限，没能单独验证思考开关，见 3.3.2；**该边界已于 2026-11-06 由第四轮"cap 2,000 × 思考开"关掉，见 3.3.4：思考开在 n=9 下没有超出裁判噪声的质量收益，而成本 +107%、生成时长中位 10s→27s ⇒ 关闭思考这个决定现在同时有质量侧与容量侧的依据**）→ S4 语义缓存（提 h）→ 生产服务器 + PG（补背压）**。⚠️ 这里原先写的是"WAL/PG"，**WAL 已按 2026-11-07 的对照实验删掉**：在"20 路并发、每路 2 写"这个形态上 WAL 净亏（吞吐 ×0.45、p95 翻倍），见瓶颈 4。

**这节的证据缺口（面试会被追问的地方）**：① **进程内**并发压测已补（2026-11-07，`_lab_load.py`，见上面"进程内并发实测"），**但入口层与百炼侧仍是空白**——没有过 werkzeug 的 HTTP 压测、也没有多 worker 形态的数据 ⇒ 上面那张 Little's law 表依旧只是量级推算、不能当 SLA；② **百炼配额未实测**（只有 4 并发离线样本，见瓶颈 1）；③ 容器内稳态检索 111ms 与宿主离线 54ms 之间那段差值**没有单独归因**（怀疑是 WSL2 文件 IO / 容器 CPU 配额，未量化所以不写进结论）。
**原来记在这里、现在已经被实测关掉的两条**：TTFT 已从"没有"变成 `llm-stream` 的 metadata 字段（样本 12.54s / 16.66s，占端到端 48.6%，但只有个位数样本、没有分布）；检索侧已从"宿主机外推 54ms"变成容器内真实 span 直读（稳态 111ms / 冷读 1.7~2.2s，见瓶颈 3）。✅ **原先记在这里的"补齐成本最低的下一条 = 对命中路径做本地并发压测"已于 2026-11-07 做掉**（`_lab_load.py`，0 token，命中与未命中各 5 档、判据 15/15 通过），实测曲线见上面"进程内并发实测"；它把第 ① 条从推断变成了实测，**但只覆盖进程内那一层**。**下一条最便宜的现在是"给命中路径过一次真 HTTP"**——起服务后用 `ab` / `hey` 打回环地址，同样 0 token，能把射程第 1 条（量不到 accept 队列与连接数上限）也关掉。

### 5.*工程化补充：可观测性与问答缓存*

> 说明：下面两项来自阶段 3 的工程化里程碑（可观测性、缓存），因为它们的效果都要靠 RAG 链路来度量，单列一节而非塞进第 3 节的优化表。

#### 5.1 可观测性：Langfuse v3 自托管埋点

**为什么自托管，而不是直接用 SaaS**：trace 的内容必然包含用户问题原文和模型回答（回答里带课程 PDF 正文片段）。把这种数据送到第三方观测平台，等于在项目之外又复制了一份完整对话库；而本项目此前刚做过一次密钥外泄的调用取证，所以"数据不出本机"的优先级高于省一次部署。

**部署形态**：独立栈 `docker-compose.langfuse.yml`，7 个服务 / 6 类镜像——`langfuse-postgres`（postgres:16，业务元数据）、`langfuse-clickhouse`（clickhouse-server:24.8，trace/observation 本体）、`langfuse-redis`（redis:7，事件队列）、`langfuse-minio`（minio，事件与导入对象存储）、`langfuse-minio-init`（一次性建桶任务，`restart: "no"`）、`langfuse-worker`（langfuse/langfuse-worker:3，异步消费写 ClickHouse）、`langfuse-web`（langfuse/langfuse:3，UI 与 SDK 入口）。**只有 web 暴露端口**（`3030:3000`），数据库与对象存储全部留在 compose 内部网络；数据落 4 个 named volume。应用侧通过 `LANGFUSE_HOST=http://host.docker.internal:3030` 跨栈上报，两个 project key 只写 `.env`（已 gitignore，仓库里只有同名空键的 `.env.example`）。

**埋点入口只有一个文件 `observability.py`**，业务代码只认它的五个函数：

| 挂接点 | 代码位置 | 产生什么 |
| --- | --- | --- |
| 每次请求 new 一个 `CallbackHandler`，塞进 `chat_graph.stream(config=)` | `app.py:127,132-134` | 一次请求 = 一条 trace，**每个图节点自动成为一个 span**；LangChain 调用会继承 callbacks，所以 `db_node` / `fc_node` 两个 Agent **一行埋点代码都没写**就有 span |
| `trace_meta("chat-request", phone)` | `graph_flow.py:69`（在 `prepare` 里） | trace 命名 + user_id / session_id |
| `generation("intent-classify", ...)` | `intent.py:27-28`，收尾 `:44` / 异常 `:48` | 意图分类的 input / output / token |
| `generation("llm-stream", ...)` | `response_generator.py:189-190`，收尾在 `finally:215-221` | 答案生成的 messages / response / token，外加 `ttft_ms` / `total_ms` / `chars` / `deltas` 四个 metadata |
| `span("retrieval", ...)` | `response_generator.py:69`，收尾 `:77-78` | **不花 token 但花时间**的那一段：路由计划、检回块数、字符总量、来源文件名 |
| `generation("summary", ...)` | `response_generator.py:279-280` | 滚动摘要压缩——**这一次调用原本是完全没有观测的**，见下面的解剖 |

后四个要手工记，是因为它们走**裸 openai client**、不在 LangChain 体系内，callbacks 覆盖不到。`_stream_llm` 顺带做了三件事：从 `choices` 为空的收尾 chunk 里取 `usage`（`usage_from` 的原则是"端点没回 usage 就返回 None，绝不拿字符数估一个假数字填进报表"）；记 **TTFT**（第一个非空 delta 的到达时刻），为的是把"排队/握手慢"和"生成慢"分开；以及把收尾放在 `finally`——SSE 客户端中途断开时生成器会被销毁并收到 `GeneratorExit`（`response_generator.py:216-217` 的注释记录了这次实测），不在 `finally` 收尾就会留下一条永远不结束的 span。

**三条安全 / 健壮性约束（这节真正的看点）**：

1. **PII 不落原文（2026-11-03 补完——这一条此前写的是失实的）**：手机号有**两条**上报通道，原来只堵了一条。`trace_user_id()` 把 trace 的 `user_id` / `session_id` 映射成 `sha256(...)[:12]`（`observability.py:15-17`），同一号码恒定映射 ⇒ 能按人聚合会话；但 `app.py:132` 把 `{"phone_number": 明文, "query": ...}` 当作**图的输入 state** 交给 `chat_graph.stream(...)`，而 LangGraph callback 会把链路的 input/output 整体记进根 observation——`trace_user_id()` 管不到这条通道，2026-11-03 就在根 span 的 Output 里读到了明文（涉及 3 条历史 trace，号码全是我自造的测试号、**不是真实用户数据** ⇒ 这是设计缺陷，不构成泄露事件）。修法是给 SDK 挂**客户端级 mask**：模块级 `Langfuse(mask=_mask_pii)`（`observability.py:47-52`），`_mask_node`（`:25-34`）按键名把 `phone_number` 换成**同一个** `sha256[:12]`（于是正文里的号码与 `user_id` 可对齐），并用 `(?<!\d)1[3-9]\d{9}(?!\d)` 兜住被拼进文本的号码，负向环视是防止误伤长数字串里的一段。**两条只能读源码得到的约束**：① mask **只在第一次初始化时生效**——`LangfuseResourceManager.__new__` 对同一 `public_key` 直接返回已注册实例并**忽略新参数**（`resource_manager.py:101-102`），而 `Langfuse._mask` 取自那个共享实例（`client.py:289`），所以先建带 mask 的、之后 `trace_meta` / `generation` / `span` 里的无参 `Langfuse()` 会继承，反过来后补则永久失效；② `CallbackHandler.__init__` **没有 mask 参数**，它靠 `get_client()` 把 `instance.mask` 传下去（`get_client.py:52`），而 `get_client()` 在"一个实例都没注册"时会自建一个**不带 mask** 的（`:107-109`）⇒ 这正是选**模块级急切初始化**、而不是包一层懒构造的原因：`callback_handler()` 比图先执行，懒构造会让无 mask 实例抢先注册。**mask 只作用于上报的那份数据，发给用户的 SSE 正文不经这里**；`_mask_pii` 的 `except` 分支返回占位符而非原值——宁可丢一条 trace 的正文，也不能把明文送出去。**实测（全程 0 token）**：用单节点 LangGraph + 生产的 `callback_handler()` 跑一次，资源管理器上注册的 mask 身份 `is observability._mask_pii` = True；样本 `{"phone_number":…, "answer":"联系 … 谢谢", "ctx":[{"t":…}], "n":42, "z":None}` 的输出里明文 0 条残留、`42` / `None` 原样穿过；Langfuse UI 的 Input / Output / Corrected Output 三处号码均已是 12 位哈希或 `<masked>` ⇒ 掩码发生在**序列化之前**，不是显示层遮一下。新增 `tests/test_observability_mask.py` 4 条纯函数用例（键名哈希 / 正文与嵌套容器 / 长数字串不误伤 / 其它类型穿透），**CI 里 `ENABLED=False` 也能跑**——为此 `_mask_node` 与 `_mask_pii` 刻意定义在 `if ENABLED:` **之外**。**残余与新副作用**：mask 只对**新** trace 生效，此前入库的 3 条明文 trace 要手工删；`db/sqlite_db.py:87` 的落库日志原来也打明文，已改成同一个 `trace_user_id()`，好处是**一行容器日志能直接跳到对应 trace**；宿主上 `ENABLED=True` 时 import 即构造客户端（起后台线程并注册 atexit flush），而 `LANGFUSE_HOST` 在宿主未必可解析 ⇒ 宿主跑离线脚本时退出阶段可能多出连接噪音，与 `tests/conftest.py` 那个坑同源，容器内不受影响。
2. **绝不写请求头**：`_Generation` 只写 `messages` / `response` / token 数与错误信息（`observability.py:81-105`）。Authorization 头里就是密钥，把它记进 trace 等于在观测平台里重演一次密钥外泄。
3. **埋点不能带崩业务，也不能污染 CI**：每个 obs 调用都包 `try/except: pass`；`ENABLED = bool(HOST and PUBLIC_KEY and SECRET_KEY)`（`observability.py:8`）为 False 时这些函数全部退化成空操作对象。这里刻意**没用 SDK 自带的 disabled client**——实测它会往 stderr 打 3 行 `Authentication error`，把 CI 日志弄脏。GitHub Actions 没有这三个环境变量，天然不需要 Langfuse；**宿主 venv 不一样，这里踩过一次，值得记下来**：`.env` 里三键齐全 ⇒ 宿主 `ENABLED=True`，而 `LANGFUSE_HOST=http://host.docker.internal:3030` **只在容器内可解析**，于是 2026-10-25 新加的那两条"关思考开关"用例（它们真的会走 `detect_intent_code` → 建一个 `intent-classify` generation）在 pytest 收尾时刷 span 到不可解析的域名，赶上 pytest 已关闭捕获流，打出 `ValueError: I/O operation on closed file` 一长串。修法是 `tests/conftest.py` **顶部**（必须排在任何会 `import config` 的语句之前，因为 `ENABLED` 在 import 时就算死了）把三个 `LANGFUSE_*` 清空。**两条判断要留下来**：一是**生产代码一行没动**——测试环境该关观测，不是让业务模块迁就测试；二是**噪音不等于污染**：查了最近 12 条 trace，全是真实问答的 `chat-request`，一条测试垃圾都没进库，因为 export 本来就失败了。

**实测（2026-10-06）**：`/api/public/health` 返回 `OK`、版本 3.225.11；容器内 `observability.ENABLED=True`、`Langfuse().auth_check()=True`；零成本打桩冒烟已产出结构完整的 trace（`chat-request` → `LangGraph` → `prepare` / `classify` / 路由 / 生成节点，节点内嵌 generation span 且 token 数正确）。

##### 5.1.1 一次 48 秒问答的解剖：埋点换来了什么

这节是埋点的**价值证明**，不是功能说明。同一老账号（历史 28+ 条，所以每次都会触发滚动摘要）、同一链路、容器内两条真实问答：

| 阶段（trace 直读） | 改前 `2b70b73c` 10-25 10:08 | 改后 `27fb0d18` 10-25 11:11 |
| --- | --- | --- |
| `prepare`（内含摘要 LLM 调用） | **20.228s** | **6.157s** |
| 　└ `summary` 生成 | 20.157s，out=**970** tok，占账 **35.3%** | 6.081s，out=**201** tok，占账 12.9% |
| `classify` / `intent-classify` | 3.802s，out=**105** tok，占账 5.3% | 0.893s，out=**1** tok，占账 2.1% |
| `rag` = `retrieval` + `llm-stream` | 24.017s（retrieval **222ms**） | 27.098s（retrieval **1.767s** 冷读） |

**RAGAS 分数写回 Langfuse Scores（2026-11-07，`_lab_scores_53.py`，0 token）——评估↔观测闭环**

所以正确解法是**离线回填**。

**前置核实（工单点名的那一步）**：7 份 csv **逐份核过表头，全都没有 `trace_id` 列**
⇒ 不能用 id 直连，必须按内容匹配。

**为什么精确匹配是可能的**：`eval_rag.py` 直接调 `stream_response_from_vectorstore`，
它内部的 `generation("llm-stream")` 在**没有 LangGraph CallbackHandler 上下文**时

⇒ 每道题一条根 trace，`input` 带 messages、`output` 是完整答案；
而收尾那句 `gen.end("".join(parts))`（`response_generator.py:238`）里的 `parts`
就是 yield 给用户的那些 delta ⇒ **`trace.output` 与 csv 的 `response` 逐字相同**。

**匹配键 = (问题指纹, 问题+答案指纹)**，各取 `sha256[:12]`，问题与答案之间用一个 NUL 字节拼接。
**只按问题指纹会撞**——9 道题在两天里问的是同一批，问题指纹两轮完全相同

**硬门槛：必须恰好命中 1 条。** 0 条或 ≥2 条一律跳过并打印原因，理由是
**分数写错 trace 比不写更坏**——它会在看板上把 A 题的分挂到 B 题上，而且挂上去之后没人看得出来。
0 命中时还刻意把原因**分成两类**打印：**问题指纹能命中但答案对不上**（多半是空格/解析差异，值得追）
与 **问题指纹也命中 0 条**（该批次压根没留下可对账的 trace，追也没用）——两种的处置完全不同。

   **规则：验证脚本绝不能用打桩/注入替被测文件补齐它缺的依赖——那样测到的是我的副本，不是他的文件。**
2. **锚点替换不幂等**：`OLD` 常常是 `NEW` 的前缀（`return EvaluationDataset(samples=samples)` ⊂

   ——数字要以 `grep -c ' PASS '` 为准，不能以我印象为准。

##### 5.1.2 层级②：把主答案的思考也关掉——一次受控对照（2026-11-03）

①做完之后 `llm-stream` 反而更突出：占单次账单 **85.1%**、端到端 **73.9%**，其中 `ttft_ms=16.657s` 单独占端到端 **48.6%**。①之所以零风险，是因为那两处调用的输出**本来就被丢弃、或只是一个结构化标签**；主答案不一样，它直接决定用户看到什么，所以这一层不能靠 0 token 探针下结论。做法是**先把"值不值得花钱验证质量"这件事量化**：跑一次受控对照拿到耗时与账单的量级差，再决定要不要为质量对照付 ¥9–20。

**对照设计（唯一变量 = `.env` 的 `QWEN_DISABLE_THINKING`）**：同一镜像（只改 `.env` 不需要 `--build`）、同一道题（LoRA 的原理与特点）、两个**都是首轮无历史、画像四字段全空**的新账号 ⇒ `scope` 同为 `be5be69f55e9`，检索与 prompt 拼装路径一致；两轮之间执行 `docker compose up -d --force-recreate`——因为 `env_file:` 是在**容器创建时**注入的，只改 `.env` 不 recreate 不生效。

**第一次尝试作废，两个原因都值得记（这是测量纪律，不是插曲）**：

1. 两轮打在**同一个未 recreate 的容器**上 ⇒ 两轮都是"思考关"，根本没有基线。
2. 第二个账号"回复特别快"其实是 **Redis 命中**：它的答案与第一个账号**逐字节相同**（826 字 vs 828 字，只差一个行尾空行），缓存载荷的 `created_at` 正是第一个账号的落库时刻，Langfuse 里也没有它的 trace（压根没调模型）。命中是**设计如此**——5.2 的 `scope` 只哈希画像四字段、故意排除手机号，所以"没填资料的访客"之间同题必然命中（1 小时 TTL 内）。**⇒ 任何延迟对照都必须先显式 `del` 缓存键、并用无历史的新账号**，否则测到的是缓存不是模型。

**四条边界（不写清楚，这张表就会被读成"免费提速 3.5 倍"）**：

1. **不是 100% 同输入**：两轮 prompt 差 36 token（1,439 vs 1,403）⇒ 检回的上下文不完全相同，量级与离线扫描记录的 **Chroma 跨进程检索抖动**一致（同一 query 的 bge 向量逐字节相同，但 k=4 时候选集会换成员，k=20 才稳）。它不影响 completion 的量级结论（1,958 vs 36），但严格说这是一次"同题对照"而非"同输入对照"。**这个抖动源已于 2026-11-06 定位并修掉，见 3.3.3**：根因是 `hnsw:search_ef` 默认 10 对 656 条的库遍历太浅，且 HNSW 图从未落盘（`sync_threshold` 默认 1000 > 656 ⇒ 持久化条件永不成立）⇒ 每个进程重建一张不完全相同的图；修法是把 `hnsw:search_ef=200` 写进两个 VECTOR 段的 `segment_metadata`，落生产后 5 个进程 × 9 题全部等于 numpy 暴力精确解。"k=20 才稳"这条旧观察也随之有了机制解释——抬 k 等于变相放宽遍历深度，治的是症状而不是根因。**本表两轮仍是修复之前的快照**，36 token 的差值不会因为修复而改变。
2. **两轮都被 `max_tokens=500` 截断**：思考开停在半句（`……LoRA 的低秩分解方式比较直观，在不少`），思考关停在光秃秃的小标题（`## 三、LoRA 的缺点与局限`），而 SSE 客户端**收不到任何截断信号**。⇒ ②省下的钱**略微高估**（不断尾的话思考关的可见 token 会更多），同时暴露出一个独立缺陷（答案被静默截断），当时单列为待办、现已修，见 5.1.3：`finish_reason` 会记进 Langfuse 的 generation metadata，生成上限也从字面量变成 `.env` 可调。**本表两轮仍是 cap=500 下的快照**，抬上限不会让这两组数字变化。
3. **质量未验证——已于 2026-11-06 关掉**（第四轮"cap 2,000 × 思考开"，见 **3.3.4**）：这张表原先只证明"快 3.5 倍、便宜 3 倍"，**没有证明答案质量没退化**。11-05 确实跑了一趟 9 题 RAGAS 付费对照（见 3.3.2），**但它同时跨越了本节的思考开关与 `RAG_MAX_TOKENS` 500→2,000 两处改动 ⇒ 不是"思考开/关"的单变量对照**，所以这条边界当时**没有被那趟跑关掉**；11-06 补跑了缺的那一格。**测到的结论是：思考开在 n=9 下换不来任何超出裁判噪声的质量收益**——faith +0.050 只有 6/9 同向（二项 p=0.254，**不显著**，且被 Q7 +0.338 / Q9 −0.186 两题主导）、relev **−0.010**、两个 context 指标全部落在 3.3.4 第 ⑥ 条实测出的噪声条内（ctxprec ±0.022、ctxrec ±0.035）；而代价是硬数：答案侧成本 **+107%**（¥0.2994 → ¥0.6202）、单条耗时中位 **10s → 27s**（最慢 87s）、`ttft` 中位 **0.8s → 11.6s**（最慢 49.7s，即用户盯空白页的时间）。⇒ **本节的生产决定（`.env` 保持 `true`）从"未验证的取舍"升级为"有质量侧依据的取舍"，方向不变**。⚠️ 但**不能反过来读成"思考开有害"**：测不到收益 ≠ 测到退化——faith / relev 这两个依赖答案的指标**至今没有同输入噪声基准**（3.3.4 第 ⑦ 条第 3 点），而 n=9 决定了小于 0.05 的均值差本就不可读。**噪声底也要按 3.3.2 第 4 条改写**：那趟跑的检索输入 `user_input` / `retrieved_contexts` / `reference` **9/9 逐字冻结**，即这里原先记的"1/9 题检索槽换文档"**那两轮没有观测到（0/9）**——⚠️ 2026-11-06 更正：0/9 是运气不是性质，检索侧当时确实存在跨进程抖动（5 个独立进程实测 Q5 4/5、Q9 2/5 换文档），只是那两轮恰好抽到同一张图，根因与修法见 **3.3.3**；真正测到的噪声在**裁判侧**——输入完全冻结时 `ctxprec` 单格仍摆动 **0.194**、`ctxrec` 摆动 **0.200**，均分层面 `ctxprec` 动了 **−0.049**。⇒ 原来写的"总分浮动 <0.02 不能当证据"**这个阈值本身偏小、已被实测否掉**：context 类指标的纯裁判噪声在**均分 0.05 量级、单格 0.20 量级**，单题变化量级约 11%。**2026-11-06 再更新：第四轮把同输入格子从 9 格扩到 25 格（3 对轮次），噪声条收紧为 ctxprec ±0.022、ctxrec ±0.035（sd/√9），单格 max 分别 0.194 / 0.286，见 3.3.4 第 ⑥ 条。⇒ 上面那句"均分 0.05 量级"要按指标分开读**：ctxprec 的均值噪声条其实只有 0.022，这里记的 −0.049 是 Q1/Q5/Q9 **三格同时跳档**凑出来的尾部事件（其中 Q1、Q9 在第四轮精确跳回原值），不是常态；分布形状是"多数为 0、偶发 ±0.2~0.29 跳档"，所以**用高斯式的"±X 阈值"去判读它本身就不合适，正确做法是逐格看有没有跳档**。

**生产决定**：`.env` 保持 `true`（思考关）；`.env.example` 的默认值也从 `false` 改成 `true`——否则别人 clone 后照模板填，跑出来的就是 58 秒那一档，与报告数字对不上。开关解析用 `config.py:71` 的白名单 `strip().lower() in ("1","true","yes","on")`，所以字符串 `"false"` 真的是 `False`（朴素的 `bool(os.getenv(...))` 会把 `"false"` 读成 `True`，这是这类开关最常见的翻车点）；代码层兜底默认仍是 `false`，即**不显式配置就不改变模型行为**。落地后容器内三处实测（`config` / `response_generator` / `intent`）都是 `True`，全量测试 **80 passed / 8.50s / 覆盖率 95%**。`tests/test_thinking_toggle.py` 为此从 2 条扩到 4 条，新增的 2 条打 `_stream_llm`（假 stream + 断言 `extra_body` 传/不传）；因为 `response_generator` 不在 `--cov` 分母里，**覆盖率仍是 95%**——加用例不加覆盖率是正常的，理由见 5.4。

##### 5.1.3 生成上限：把"静默截断"变成可观测、可配置（2026-11-03）

**缺陷**：RAG 主答案的 `max_tokens` 是写死在 `response_generator.py:116` 的字面量 `500`，而 `finish_reason` **全项目没有任何一处读它**——不是前端把它忽略了，是服务端从来没取过。于是截断在三个层面同时隐形：SSE 客户端只收到 `[DONE]`（`chat.js:149`），Langfuse 里只有 token 数，日志里什么都没有，唯一的线索是"答案刚好停在 500 token、结尾是半句话"。5.1.2 那两轮就是这么被发现的（边界 2）。

**为什么它比"贵"更值得修**：`max_tokens` 是全项目唯一一处**付了钱却拿不到货**的设置——上限写满时，你为 500 个 output token 付了费，拿到的是一段没有结尾的文本，而且没有任何信号告诉你它没写完。贵至少是看得见的。

**改法（两步，都 0 token）**：

1. **可观测**：`_stream_llm` 从每个 chunk 的 `choices[0]` 上读 `finish_reason`（`:222`），连同派生出的 `truncated`（`== "length"`）一起写进 `gen.end(metadata=...)`（`:244-245`）。截断从此是 Langfuse 里**一个能筛的字段**，不必再靠答案长度反推。两个实现细节都是被现有代码逼出来的：取值用 `getattr(choice, "finish_reason", None)` 而不是直接点属性，因为真实端点每个 chunk 都带这个字段，而已有的 `tests/test_thinking_toggle.py::_FakeStream` 是 `SimpleNamespace` 造的、没造它，直接点属性会把那两条测试打挂；`finish` 的初始化放在 `try` 之外（`:197`），因为 `finally` 要引用它——若 `create()` 本身抛异常，循环一次都没进过，那个名字就是未定义的，`finally` 里会再抛一次 `NameError`，把真正的异常盖掉。
2. **可配置**：三个字面量（RAG 500 / 闲聊 300 / 联网 800）提到 `config.py:77-79` 的 `RAG_MAX_TOKENS` / `CHAT_MAX_TOKENS` / `WEB_MAX_TOKENS`，各带同名 `.env` 覆盖，**默认值与提取前逐字相同** ⇒ 这次改动对线上行为是中性的（容器内实测三个值仍是 `500 300 800`）。这么做的目的不是"以后好调"，而是让**抬高上限变成一次 `.env` 改动 + `--force-recreate`**，与 `QWEN_DISABLE_THINKING` 同一套回滚路径，不必再动代码。

顺带一次事实核对：**"按意图分档"本来就是现状**（RAG 500 / 闲聊 300 / 联网 800 / 滚动摘要 500，`response_generator.py:304` / 意图分类 10，`intent.py:28`），所以它不是一个待选方案；真正被质疑的只有 RAG 那个 500。

**上限抬到多少：本轮不定，等一次付费跑给出数据**（该跑已于 2026-11-05 完成，结论见本节末尾的"上限落地"与 3.3.2；下面这张表是**跑之前**按最坏情况估的，原样保留以便与实测对照）。按 5.1.2 那两轮的 token 与账单反推出的单价（input $1.690/M、output $5.071/M，用第三个独立数据点交叉验证，差 $0.000001；汇率 7.1），在思考关、prompt 1,403 token、**答案写满上限**的最坏情况下，单次 RAG 请求的成本是：cap 500 → ¥0.0348；800 → ¥0.0456（×1.31）；1,000 → ¥0.0528（×1.52）；2,000 → ¥0.0888（×2.55）。9 题跑一遍分别是 ¥0.31 / ¥0.41 / ¥0.48 / ¥0.80 ⇒ **抬到 2,000 只多花 ¥0.49**，相对 RAGAS 裁判那 ¥9–20 属于噪声级。所以抬上限不单独试，与 3.3 那次质量评估合并成同一趟付费跑：一次拿到质量分、自然答案长度分布、真实截断率三样东西，再按数据定生产上限。

#### 5.2 问答缓存：Redis

**动机**：一次知识库问答在未命中缓存前要花 **2 次 LLM 调用**（意图分类 + 生成），实测未命中端到端 **70.3s**（`qwen3.8-max` 是思考型模型，思考 token 也计入输出）。客服场景里重复问题高度集中，缓存是唯一既降延迟又直接降账单的位置。⚠️ **70.3s 是"思考开 + cap 500"那一档的数**（本节与 4.2 的吞吐表都引用它）：5.1.2 关掉主答案思考、3.3.2 抬开生成上限之后，同一条路径的量级已降到 **约 6~16s（均值 ≈11s）**，但**没有按生产链路重测**，所以本节保留原值当历史实测，不按新数改写——缓存的相对收益（0.1s vs 十余秒）仍然是两个数量级。

**图拓扑**（`graph_flow.py:160-179`）：

```
START → prepare → cache_lookup ─（命中）→ cache_hit ─────────────┐
                              └（未命中）→ classify → rag|web|db|fc|chat ┤→ finalize → END
```

**读放在 `classify` 之前**是整个设计的核心决定，它带来两点收益、也带来一个必须先证明的安全性：收益是命中时把分类与生成两次调用一起省掉；安全性依据是 `detect_intent_code(query)` 只吃 query、不看历史，**是 query 的纯函数**，所以"同一问题 ⇒ 同一意图 ⇒ 同一答案"成立，读端无需先分类。反过来，写端用 `intent == 1` 收窄（只缓存知识库问答），读端不设限——**是写入侧变窄让读取侧免分类变得安全**，这两条门禁是一对。

**key 设计**（`qa_cache.py:26-61`）：`"aicrm:qa:v1:" + sha256(normalize(query) + "\x00" + scope + "\x00" + CONFIG_FP)[:32]`

- `normalize()` = NFKC 全角转半角 → `casefold()` → 去掉**所有**空白 → 去首尾标点。于是 `RAG 是什么？` 与 `rag是什么` 命中同一条。代价是只差空格的两个英文问题会撞在一起，可以接受。
- 前缀带版本号 `v1`：归一化规则或 payload 结构以后改了，换前缀就能让旧缓存整体失效。
- 原始问题**不出现在 key 里**（问题里可能带手机号），定长且无特殊字符；`\x00` 作分隔符，避免"问题尾字符 + 签名首字符"拼出同一个串的歧义。
- **`scope` = 用户画像签名**（`graph_flow.py:48-56`）：`stream_response_from_vectorstore` 会把姓名 / 年龄 / 职业 / 兴趣拼进 system prompt（`response_generator.py:91、116`），也就是说**答案文本本身受用户画像影响**。不带签名的全局缓存会把 A 的个性化答案推给 B——既是内容串号，也是 PII 外泄。签名只取这四个字段、**故意排除手机号**：手机号进签名等于零跨用户命中，还让 PII 出现在 key 里。四项全空的访客签名恒定，所以演示与评估里最常见的"没填资料的提问者"之间仍能命中。
- **`CONFIG_FP` = 配置指纹**（`qa_cache.py:32-41`，2026-11-07 补）：答案不只由 query 与画像决定，**检索侧**（`EMBEDDING_MODEL`、`CHROMA_PERSIST_DIR`、`TOP_K_SINGLE` / `TOP_K_SHARED` / `LOSER_DUAL_THRESHOLD`）与**生成侧**（`MODEL_NAME`、`RAG_MAX_TOKENS`、`QWEN_DISABLE_THINKING`）共 8 个档位同样决定它。把这 8 项拼串取 `sha256` 前 8 位当 key 的第三段，改任何一档就整体平移到新 keyspace——旧条目立刻永不命中、按 TTL 自己过期，不再依赖谁记得去 `clear()`。指纹是配置的**纯函数**，所以回滚到旧值会重新命中尚未过期的旧条目（正确：答案本来就一样）。刻意排除 `JWT_SECRET`（未设置时每次启动随机 ⇒ 会让缓存每次重启全废）与 `LANGFUSE_*`（埋点不改变答案文本）。四项覆盖不到的残余见本节末"已知边界③"。

**写入四道门禁**（`graph_flow.py:148-150` + `qa_cache.py:106-122`）：① 意图 1；② **只在首轮**（`history` 为空 ⇒ `summary` 也为空 ⇒ 答案确实是 query + 画像 + 知识库 的确定性函数，不带对话痕迹；非首轮的答案嵌着该用户独有的上下文，缓存出去等于把一个人的对话焊成所有人收到的回答）；③ 答案非空；④ **含兜底道歉文案的不写**——`_stream_llm` 在异常时会把"抱歉，我现在无法处理…"当成答案 yield 出来（`response_generator.py:201-204`），这种负面结果进缓存等于把一次偶发故障固化成一小时，而且它看起来像"缓存生效"，比空答案更危险。命中路径不写缓存（它没走 `classify`，`intent` 缺席，`None != 1` 天然跳过），所以热条目不会被反复续期、绕过 TTL。

**降级优先于命中**：`REDIS_URL` 为空时整个模块 no-op（该变量只由 compose 的 `environment:` 注入、不进 `.env`，因此宿主 venv 与 CI 读到空字符串，不需要装 Redis）；客户端是懒加载单例，连接与读写超时都是 **0.5s**——读缓存不该拖慢首 token；任何异常一律吞掉当作"没命中"。原则一句话：**缓存不能把一次本来能成功的回答变成失败**。

**运维边界**（`docker-compose.yml:28-39`）：`redis:7-alpine`；**故意不写 `ports:`**——缓存 value 里是完整答案文本，没理由把 6379 暴露到局域网，容器间用服务名即可；`--save "" --appendonly no` 关掉全部持久化（缓存值可由 LLM 重建，落盘只扩大内容外泄面，不带来回滚收益）；`--maxmemory 64mb --maxmemory-policy allkeys-lru`——Redis 默认 `noeviction`，缓存写满后 `setex` 会直接报错、命中率归零；`depends_on: redis: condition: service_healthy` 配 `redis-cli ping` 健康检查。

**副作用顺序（一次事故换来的）**：本项目有一条不变式——**流出去的字 == 存进历史的字**。命中路径也走同一个 `_stream_out`（`graph_flow.py:99-103`）而不是另开一条 `return`，就是为了守住它。缓存写入最初放在 `rag_node` 里，比 `finalize` 的 assistant 落库**早一个节点**；实测遇到过一次"服务端已生成并写入缓存、客户端却在两个节点之间断开"的运行（容器日志有 `POST /chat 200`、该号码只有 user 行没有 assistant 行，而几分钟后另一个全新用户问同一题直接命中，证明缓存确实写进去了），留下"缓存有、历史缺"的悬挂问题。现已把 `put` 挪进 `finalize`、**落在历史之后**（`graph_flow.py:146-150`），最坏退化成"历史全、缓存无"，代价只是下次多付一次生成。

#### 5.2.1 语义缓存阈值的离线扫描：为什么"加个余弦阈值"被数据否掉了

**要回答的问题**：把 key 从"归一化后精确命中"换成"归一化 + 与已缓存 query 余弦 ≥ 阈值"，阈值定多少才不会把两道不同的题当成同一道。误命中的代价是**非对称**的——它把 A 题的答案原样推给 B 题提问者，而且**看起来像缓存正常生效**，比一次未命中严重得多（和 `qa_cache.put` 拒绝兜底文案是同一条理由）。

**测法**（脚本 `_lab_semantic_threshold.py`，本地 `bge-base-zh-v1.5`，0 token）：35 条课程领域问题，按 `(域, 主题簇)` 两两配对生成三组带标签样本——`SYNONYM` **同题不同打字**（该命中，41 对；其中归一化后已经精确相等的对被剔除，所以这里的召回就是语义层相对精确层的**增量**）、`NEAR` **同域但问的不是同一件事**（不该命中，319 对，误命中的主战场）、`CROSS` 跨域（不该命中，234 对）。全部两两算余弦，不靠我认为。

**核心数字（无前缀 / 对称语义口径）**：

| 分组 | 该不该命中 | min | 中位 | max |
| --- | --- | --- | --- | --- |
| `SYNONYM` 41 对 | 该 | **0.3388** | 0.6658 | 0.9256 |
| `NEAR` 319 对 | 不该 | 0.1546 | 0.3248 | **0.7043** |
| `CROSS` 234 对 | 不该 | 0.1229 | 0.2862 | 0.5443 |

两组**直接重叠**（0.7043 > 0.3388），所以不存在"一个阈值同时满足不误命中、又保住召回"的解。阈值扫描（计数不是四舍五入的百分比——我第一版把 1/319 印成"0%"，差点把误命中读成没有）：

| 阈值 | 增量召回 SYNONYM | NEAR 误命中 | CROSS 误命中 |
| --- | --- | --- | --- |
| 0.66 | 21/41 = 51.2% | 1/319 | 0/234 |
| **0.70** | 16/41 = 39.0% | **1/319** | 0/234 |
| **0.71** | 15/41 = 36.6% | **0/319** | 0/234 |
| 0.80 | 7/41 = 17.1% | 0/319 | 0/234 |
| 0.90 | 3/41 = 7.3% | 0/319 | 0/234 |

也就是说：**本批语料上零误命中的最低阈值是 0.71**，代价是增量召回只有 36.6%，而阈值再往上就迅速掉到"几乎没有增量"（0.80 只剩 17.1%）。

**越界的那一对长什么样**（这决定了我为什么不敢上）：`chunk 切分策略` vs `ZeRO 的切分策略` = **0.7043**——共享"切分策略"四个字，问的却是完全两个东西；第二危险的是 `ReentrantLock 能中断吗` vs `sleep 能中断吗` = 0.6563。这正是本项目知识库里最常见的形态：**同一批术语在不同主题下反复出现**。

**两条试过的"救阈值"的路，都没救活**：

1. **加 bge 的检索前缀**（`为这个句子生成表示以用于检索相关文章：`）：SYNONYM min 反而从 0.3388 降到 0.3120、NEAR max 从 0.7043 升到 **0.7376** ⇒ 分布更重叠。**检索型前缀不适合 query-query 的对称比较**，这个口径要固定成"无前缀"。
2. **再叠一个字符 bigram Jaccard 门控**：j=0.20 时零误命中的最高召回只有 **20%**，比纯余弦的 36.6% 更低——词面重合要求会把"换了说法"的正主一起切掉。**负收益**。

**结论与替代判据（尚未实现、也还没验证）**：缺陷不在阈值大小，而在**判据本身**——只比"问题像不像"，没有比"它们要的是不是同一份材料"。所以 S4 如果还要做，正确改法是把命中条件换成 `cos ≥ 0.75` **且** `两题检回的 top-1 来源文档相同`。第二条不需要额外调用：`kb_router.retrieval_plan` 和向量检索都是 query 的纯函数，仍然可以放在 `classify` 之前，所以"命中就连意图分类一起省掉"这个核心收益不变，只是未命中时要多付 **54ms**（见 4.2 瓶颈 3 的离线量测）去把候选的 top-1 来源查出来。

**这批语料自身的局限（必须先讲，否则数字会被过度解读）**：`SYNONYM` 是我**刻意换着说法**写的，比真实用户的重复提问更极端 ⇒ 表里的召回是**下界**；反过来 `NEAR` 里越界的只有 1 对、553 个"不该命中"样本也只有 1 对越界 ⇒ **0.71 之上"零误命中"不能当保证**，只能说没测出来。任何上线前都要在**真实历史 query** 上重扫一遍（`crm.db` 的 `chat_history` 就是现成语料，注意里面的原始问题可能带手机号，只做哈希/长度级统计，不进仓库）。

#### 5.3 容器化与镜像瘦身

**运行形态**：`Dockerfile:2` 用 `python:3.9-slim`（3.9 对齐本地 venv 与 CI，避免"我机器上能跑"），`Dockerfile:6-8` 单独补 `libgomp1`——`sentence-transformers`/`torch` 运行时依赖 OpenMP，slim 镜像默认没有，缺它会在 import 阶段报 `libgomp.so.1: cannot open shared object file`。`Dockerfile:15` 先只拷 `requirements.txt` 再装依赖，是为了让"改代码重新 build"命中依赖层缓存；反过来先拷代码会让几百 MB 的层每次失效。启动命令是 `Dockerfile:44` 的 `CMD ["python", "app.py"]`，代价在 4.2 瓶颈 2 里已经量化过（开发服务器无线程池/无背压），是演示阶段的刻意取舍，不是疏漏。

**两处挂载而不是 COPY**（`docker-compose.yml:25-26`）：391MB 的中文嵌入模型 `../chinese_model` 以**只读**方式挂进 `/app/chinese_model`，`./data` 整体可写挂载。理由分两层——模型体积 COPY 进镜像等于给每次构建加一层死重；而 `data/` 里的向量库和 SQLite 是**状态**，打进镜像会让"容器删了数据还在"变成"数据删了容器还在"。`docker-compose.yml:17` 用 `environment` 覆盖 `EMBEDDING_MODEL` 为容器内绝对路径，因为 `environment` 优先级高于 `env_file`，宿主 `.env` 里那条相对路径在容器内是错的。

**镜像瘦身：一个 184MB 的 wheel 被打进两层**。国内没有任何可用的新版 torch CPU 镜像源，只能手动下 wheel 离线装，而这一步最初写成 `COPY torch.whl /tmp/` + `RUN pip install`。第一版实测镜像 **2.9GB**，`docker history` 里能看到两份 184MB：一份来自那条 `COPY`，另一份来自 `Dockerfile:36` 的 `COPY . .` 把项目根的同一个 wheel 又拷进 `/app`。关键认知是**镜像层不可变**：`COPY` 之后补一句 `RUN rm` 只是在新层里标记删除，那 184MB 仍然算在镜像体积里，回收不掉。

最终改法是三层配合（`Dockerfile:19-31` + `docker-compose.yml:5-10` + `.dockerignore:24-30`）：

1. wheel **移出项目目录**，放到同级的 `../docker_wheels/`；
2. compose 用 `additional_contexts: wheels: ../docker_wheels` 声明一个**命名构建上下文**；
3. Dockerfile 用 `RUN --mount=type=bind,from=wheels,...` 装它——bind mount 只在那一条 `RUN` 期间可见，不进任何层。

这里踩过两个坑，都是"看起来更简单的写法"：

- `target=/tmp/torch.whl` 这种短名会直接 `ERROR: Invalid wheel filename (wrong number of parts)`，pip 按 `名字-版本-py标签-abi-平台.whl` 校验文件名，**target 必须保留完整 wheel 文件名**。
- 本以为"wheel 留在项目根 + `.dockerignore` 排除 `*.whl`"就够了，实测**不行**：`.dockerignore` 的排除对 `RUN --mount=type=bind` 同样生效，build 报 `failed to compute cache key ... not found`。也就是说 `.dockerignore` 影响的不止 `COPY`/`ADD`。`*.whl` 这行现在留着当**兜底**——万一有人把 wheel 又下回项目根，它会让 build 在装 torch 那一步明确报错，而不是悄悄变成一层 184MB 的隐身胖层。

**改后数字（2026-10-03 当时记录，非本轮复测）**：镜像 **2.9GB → 2.54GB**，`COPY . .` 层从 184MB 降到 **225kB**，torch 那条 `COPY` 层整层消失；剩下的 torch 安装层 826MB + 依赖层 739MB 是运行时代价，不可省。最后一轮 `docker compose build` 只花 **10.5s**（依赖层全 `CACHED`，缓存键按内容校验和判定），全量重建 207.5s。另外一个容易读错的点：`docker history` 的层大小**加不出** `docker images` 头条那个 SIZE（共享层去重 + 虚拟大小口径不同），别拿层和去对账。

**跨平台一致性**：`.gitattributes` 把仓库内一律锁成 LF，并对 `Dockerfile`/`*.yml`/`*.py` 等强制 `eol=lf` 检出。原因是 Windows 上 `core.autocrlf=true` 会把检出文件变成 CRLF，而带 `\r` 的 Dockerfile 会让容器内脚本以 `/bin/bash^M: bad interpreter` 这类难以定位的形式失败——锁死行尾之后，别人在 Windows 上 clone 也能直接 `docker compose up`。

**已知边界**：CI 里**不跑** `docker build`，所以"镜像能构建起来"这件事没有被自动化验证过，只被本机手动验证过；容器内也没有集成测试（测试全部跑在宿主 venv 上）。

🔴 **2026-11-07：项目历史上第一次 CI 红灯（run #27 on `a9d3d45`，step 5 "Run tests" exit 1）。**
讽刺的是 `a9d3d45` 只改了本报告（markdown），失败来自同一次 push 带上去的 `f6804a3`
（新增 `tests/test_max_tokens_wiring.py`）——**一次 push 只在 head sha 上跑一个 run**，
所以红灯挂在一个"看起来无害"的提交上。

**根因**：该文件的 `captured` fixture 打桩了 `rg.bocha_search`，**没有打桩 `rg.BOCHA_API_KEY`**；
而 `response_generator.py:142` 是 `if not BOCHA_API_KEY: yield "网络搜索功能未配置…"; return`，
它在调 `bocha_search` **之前**就短路了。CI 上没有 `.env`（被 gitignore）⇒
`config.py:21` 的 `os.getenv("BOCHA_API_KEY", "")` 得到空串 ⇒ 短路 ⇒ `_stream_llm` 一次都没被调用 ⇒
`captured == []` 而不是 `[(0.5, 800)]`。**本地绿是因为本地有 `.env`。**

**复现与验证（都是 0 token、不出网）**：

| 步骤 | 命令 | 结果 |
|---|---|---|
| CI 日志 | 匿名 `api.github.com/.../actions/runs/{run_id}/logs` | **HTTP 403**（需鉴权）⇒ 拿不到日志，改用同条件本地复现 |

| 全量审计 | 同上并清空另外四个键 | **1 failed, 89 passed** ⇒ 只有这一条有隐藏依赖 |
| 修法预验 | `_lab_fix_check_61.py`：不改测试文件，手工做同样四个替换 | 不加那行 → `[]`；加上 → `[(0.5, 800)]`，`VERDICT: 修法有效` |

**修法**：fixture 里加一行 `monkeypatch.setattr(rg, "BOCHA_API_KEY", "test-key-not-real")`。

**这次的教训比这个 bug 本身值钱**：① 一个**为了钉住接线而新写的测试**自己引入了环境依赖，
而 CI 恰好抓住了它——"CI 有什么用"这个问题被它自己演示了一遍；
② 打桩纪律原先写的是"只替最外层那个出网调用"，这条不够：**还要替掉所有"从 config 读、
且会在出网之前改变控制流"的开关**，否则被测函数根本走不到那个出网调用；
③ README 顶部那个徽章在修好之前一直是红的——公开仓库上红灯的代价不只是 CI 本身。

🔴 **#62：同一缺陷类的第二例——"自以为钉住了，其实一行都没钉"（2026-11-07，变异测试实测）**。
#43 把配置指纹并进缓存 key 的第三段（`qa_cache.py:60` 的 `raw = normalize(query) + 分隔符 + scope +

**实测（`_lab_mutation_fp.py`：进程内把 `_key` 换成"删掉指纹段、其余逐字照抄"的变异版，再跑全量）**：

|---|---|---|---|

第二行那次的失败信息里，变异 key 与基线 key 逐字符相同（同一个 32 位十六进制值），断言的"必须不等"因此为假

**没有杀伤力的绿灯等于没测过**；能给一致性/接线类修复当验收的，只有一个能主动破坏它的装置。
